## Context

PRD §4 定义了 12 层标签体系，并明确「12 层体系展示层级图与打标覆盖率」是成果原则之一。但标签体系的**总规模**直接决定 system prompt 的长度，而 system prompt 是**每一条内容都要付的固定成本**。

PRD §10-Q2 给出的原始测算：

> §4.3 建议 L1=20、L2=60~80、L3=150~250、L4=400~800、L5-L12 每层 50~300，总量 1500~2500。2000 个标签的描述按每条 30 字估算 ≈ 6 万字 ≈ 4-6 万 token，**每条内容都要付这个成本**（× 每日数万条 = 主要成本项）。

进一步分析：

| 规模 | system prompt token（估算） | 日均 3 万条内容的 token 成本（按 GLM-4-Flash 免费档/自建） | 打标质量影响 |
| --- | --- | --- | --- |
| 500 | ~1.2 万 | 低 | L4 粒度不足，区分度差 |
| 1200 | ~2.4 万 | 中 | 尚可 |
| **1800** | **~3.6 万（未分片）** | **高** | 良好 |
| 2500 | ~5 万 | 很高 | 良好但成本失控 |

关键矛盾：**L4 及以下的深度标签是区分度的来源，但也是 prompt 长度的主要贡献者**。而 §4.1 的层级设计已经给出了破局点 —— **L1–L4 是严格树，L4 的合法分支完全由 L1–L3 决定**。

量化：一个 L3 节点平均有 2–4 个 L4 子节点；一个 L3 节点平均有 2–3 个 L4 子节点。也就是说：

- L1–L3 全量 = 20 + 70 + 200 = **290 个标签**
- 剩余 550 个 L4 分布在 200 个 L3 节点下 → 平均每个 L3 下 2.75 个 L4

**结论：给定内容后，候选 L4 的合法集合最多只有 ~10 个**（2–3 个 L3 分支 × 2–4 个 L4）。所以没有必要把 550 个 L4 全部塞进 prompt。

## Decision

**标签总量锁定 1200–1800；采用「L1–L3 全量 + L4 及以下按需检索 top-N 注入」的分片装载策略，把 system prompt 压到 1.5–2 万 token。**

具体分层策略：

| 层 | 数量 | 装载方式 | 理由 |
| --- | --- | --- | --- |
| L1 | 20 | **全量注入** | 顶层领域，数量小，单选，必需 |
| L2 | 70 | **全量注入** | 一级类目，单选，必需 |
| L3 | 200 | **全量注入** | 二级类目，候选空间的核心 |
| L4 | ~550 | **按需 top-N 分支注入** | 由 L1–L3 决定分支，每条内容只需 ~3 个分支 |
| L5–L9 | 各 20–40 | 按需 top-N | 实体类，靠语义相似度召回候选定义 |
| L10 | ~60 | **不进召回特征**（PRD §4.1 明文） | 只进画像，抽取式属性由规则通道单独处理 |
| L11 | ~40 | **全量注入** | 消费意图，强特征且数量小 |
| L12 | ~40 | **全量注入**（含互斥组） | 情感立场风险，强特征；互斥组需要完整呈现 |

**装载算法**（实现于 `labeling/prompt_builder.py`）：

1. 渲染**常驻分片**：L1 + L2 + L3 + L11 + L12 的 `code / name / description / 配额 / 互斥组`。
2. 渲染**规则段**：C1/C2/C6 的自然语言表述 + 冲突示例（来自 `label_def.version`）。
3. **检索增量分片**：用内容向量在「L4+ 标签定义中心向量」上做 ANN，取 top-40 → 按 L1–L3 分支聚合 → 取 **top-3 个分支** → 注入这 3 个分支下的 L4 定义及其子孙描述。
4. **预算守卫**：估算 token 数（中文 ≈ 0.75 token/字 + 15% 结构开销）。若仍 > 20000，依次收缩：分支数 3→2→1 → 缩减每分支 L4 数量 → 记录 `prompt_budget_exceeded=true` 并告警。
5. **绝对约束**：约束段（C1/C2/C6）与输出 Schema 段**永远不被裁剪**。宁可少注入标签定义，也不可让规则约束消失。

**版本解耦**（PRD §4.6 的关键决策，落实为工程约束）：

| 段 | 版本归属 | 变更者 |
| --- | --- | --- |
| 角色定义 + 输出 Schema | `prompt_version` | 算法工程师 |
| 标签体系定义 + 规则约束 + few-shot | `label_def.version` | 内容运营 |
| 待标内容 + 辅助信息 | 无版本 | — |

两者独立版本化，使得「运营改标签」与「算法改提示词」互不干扰——这是 P4-TAG-006 灰度双版本能成立的前提。

## Consequences

### 正面

- **prompt 长度可控在 1.5–2 万 token**，相对 2500 标签的 5 万 token 节省约 60%。
- **成本随之下降**：单条 token 成本（EE-02）与总成本（EE-11）直接受益。配合 `deterministic` 默认档，演示环境成本为零。
- **区分度不损失**：L4 的候选空间由内容语义决定，检索注入比全量注入**更精准**（不会出现「567 个 L4 定义里挑花眼」的选择困难）。PRD §4.1 的「单层内标签语义不重叠（避免同层歧义导致随机选择）」得到强化。
- **新增标签零重启生效**（P4-TAG-001 / NF-E03）：标签走 DB，改完即生效；分片检索是动态的，不需要重新生成 prompt 模板。

### 负面 / 代价

- **引入了一个检索环节**，标签体系不再是「纯静态注入」。这意味着打标链路依赖向量检索可用性 —— 必须处理「检索不可用」的降级（退化为只注入 L1–L3 全量，牺牲 L4 精度但不失败）。
- **L4 检索的召回率成为新的质量瓶颈**。若内容向量质量差（`hashing` 后端），L4 检索会召回错误分支，导致 L4 打标错误。**因此 `hashing` 后端下的结果必须在评测报告中单列**，不能与 BGE-M3 结果混算。
- **多一个可调参数**：top-3 分支、top-40 ANN 候选、20000 token 预算。这三个参数需要压测调优。
- **标签体系种子的撰写工作量集中在 L1–L3 与 L11–L12**（330 个标签需要高质量描述），L4 的 550 个标签只需要简短描述 + 1–2 个示例 —— 这一点降低了整体标注成本。

### 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 分支检索召回到错误分支 | 分支选择由 L1–L3 全量 prompt 引导（LLM 先定层），L4 注入只在其合法子树下；且 L4 标签的 `path_prefix` 保证注入的标签都是合法后代 |
| token 估算偏差导致超窗 | 估算器对中文/英文分别计权 + 15% 结构开销 + 预算守卫 + 触发「上下文超长 → 二次尝试（只取首块 + 摘要）」的既有降级路径（PRD §5.2） |
| 标签总量膨胀突破 1800 | 体系发布时校验总量区间，超出则**拒绝发布**（`labeling/taxonomy.py` 的 `validate_release()`） |
| 检索不可用 | 降级为「仅 L1–L3 全量注入」，打标继续（精度下降，不失败），并在 `content.pipeline_version` 记录降级状态 |

## Alternatives Considered

| 方案 | 为何被否 |
| --- | --- |
| **总量 1500–2500，prompt 全量注入（PRD §4.3 原建议）** | ① 单条成本 4–6 万 token × 每日数万条 = 主要成本项，直接击穿 §1.4 风险对策 R1；② 567 个 L4 定义同时呈现会加剧 §4.1 所担心的「同层歧义导致随机选择」；③ 本地 14B 模型的上下文窗口压力巨大（Q4 基准无独显）。 |
| **总量 500–800 的小体系** | 区分度不足。PRD §4.3 明确「低于 1500 区分度不足」；L5–L12 每层需要承载实体/属性/意图/情感，500 根本放不下。 |
| **两阶段打标（先分类到 L3，再对 L3 子树细分）** | 理论上更省 token，但引入两次 LLM 调用 → **延迟与成本翻倍**，且两次调用的错误会级联（第一阶段分错 L3，第二阶段必错）。本方案在**单次调用内**用检索替代「两阶段」，是更优的折中。 |
| **让 LLM 自己检索标签（工具调用 / function calling）** | ① 需要模型支持工具调用，削弱了 `deterministic` 后端的对等性；② 工具调用的不确定性破坏 `temperature=0` 的可复现承诺（§14.8 要求逐位一致）；③ 多轮调用的延迟不可控（SP-03 要求 LLM P95 ≤ 10s）。 |
| **用 LLM 的长上下文（128K）一次性塞满 2500 个标签** | ① 成本未解决（仍是 5 万 token）；② 「大海捞针」式注意力的准确率低于「精准呈现少量候选」；③ 本地 14B 模型的 128K 上下文在 16 GB 内存的 CPU 推理下不可行（Q4）。 |
| **把标签定义放在 RAG 知识库里，靠向量库自己检索** | 与 ADR-0004 的自写编排决策冲突（不引入框架）；且完全依赖向量质量，没有「L1–L3 树形结构」这一确定性约束，破坏 C1/C2 的可解释校验。 |
| **按字符数而非 token 数截断 prompt** | 不精确，且会破坏 JSON Schema 段与规则段的完整性。 |
